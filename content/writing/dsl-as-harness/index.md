## 一个窄论点

2025 到 2026 年，应用 AI 工程领域有一个共识在形成，Agent 跑在什么环境里比它用什么模型更重要。Harness 就是那个环境，Agent 能调用的工具、接收信息的格式、捕获错误的反馈、让未来的自己接手的脚手架。同一个模型，换一个更好的 harness，产出的工作质量差异巨大。

这篇文章要论证一个更窄的点，域特定语言是你能给 Agent 的最强 harness 之一，恰恰因为它放弃了通用性。DSL 用有限、可读、可校验的表达面，替换掉通用代码的无限表达力。这个取舍，正是自主 Agent 长期可靠运行的前提。

## 为什么放弃通用性反而赚了

通用编程语言是图灵完备的。这是它的荣耀，也是 Agent 的风险。同一个行为有无穷种写法，不同代码库的约定互不相同，语言本身不会告诉你一段程序对这个领域是否正确。Agent 很自由，自由加上不确定性就是甩开手到处摸索，它们广泛探索、飘向局部合理的模式、积累细微错误，然后这些错误在很久以后才暴露。

DSL 把这些性质全部翻转了。它刻意不是通用语言。它能表达一组有限的事物，用有限种方式，通常自带 parser 和 validator，可以在任何代码执行之前说"这个结构是合法的"或者"这个不合法"。你给 Agent 一个 DSL，不只是给了它一个工具，你重新塑造了它需要搜索的空间。这种重塑，让四种经典 harness 模式从同一个设计决策中自然浮现出来。

### Schema 就是记录系统

Harness 工程的第一条原则是，Agent 在上下文中读不到的东西等于不存在。意图必须活在机器可读的制品里，不能活在 Slack 线程或者某个人的脑子里。DSL 天然满足这一点，它的 schema 就是规格说明书。Agent 写下一个 DSL 文档时，用户的意图被捕获成结构化、可检查的对象，而不是溶解在命令式代码的细节里。你可以 diff 它、版本控制它、校验它、推理它，不需要执行它。

### Validator 是免费的反馈回路

SWE-agent 研究中最高杠杆的组件，是每次编辑都跑的 linter。它在错误被引入的那一刻就拒绝语法损坏的变更，不让错误在后续的十几个步骤中传播。DSL 让这个回路变成免费的。每个 DSL 都有 parser，大多数有类型或 schema checker。Agent 输出的瞬间，如果结构不合法，立刻被拒绝，附带一个定位精确、可操作的错误信息。你不需要搭这个反馈回路，它跟语言一起打包发过来的。

### 语法是强制函数

SWE-agent 的搜索工具限制了结果数量，在查询太宽泛时告诉 Agent 去收窄。这个限制不是缺陷，它是强制函数，把 Agent 从胡乱摸索推向有意识的具体行动。DSL 的语法对整个输出是一个强制函数。因为词汇有限，幻觉的空间从结构上就变小了。Agent 不能发明一个语法里不存在的选项，它只能组合语言真正提供的基本单元。在这里，约束是特性。

### 语言的粒度就是上下文的粒度

渐进式披露原则是，先小后大，只在需要时展示更多，是对"把整个项目塞进上下文窗口然后稀释 Agent 注意力"的解药。一个设计良好的 DSL 有天然的分解结构，beat、service、rule、step。这种粒度成为 Agent 的编辑单元。它可以只处理一个片段，不需要在脑子里装下整个文档。语言的本身结构，而不是临时拼凑的启发式规则，定义了这些接缝。

## 三个例子

### MulmoScript，生成和执行的干净分离

MulmoScript 是一个基于 JSON 的 DSL，用来描述多模态演示和视频，一系列 beat，每个 beat 携带文本、图像、音频和时间信息。它之所以值得作为 harness 案例，是因为它支持的架构，Agent 不产出视频，Agent 产出脚本。一个确定性的渲染器把脚本变成最终制品。

这个分离把整篇文章的论点做成了具体的东西。概率性的创造性工作，决定视频该说什么、展示什么，由 Agent 在 DSL 中完成。确定性的、可重复的工作，渲染像素和音频，由从不猜测的代码完成。输出在渲染第一帧之前就可以审查，同一个脚本永远产生同样的视频，糟糕的结果可以被 diff、编辑、重新渲染，而不是从头生成。Harness 的口号"模型决定想什么，harness 决定怎么执行"，在 MulmoScript 里是流水线中一个真实的边界。

### Collections，用户自己写 Harness

MulmoClaude 的 collections 功能是一个 DSL-as-harness，它的写法被交给了最终用户。一个 collection 由一个 schema 定义，一个描述数据形状的小 DSL，字段和类型、它们之间的关系、哪个值标记一条记录为"完成"、什么时候发通知、一条记录怎么循环、如果是 feed 类型，从哪个源拉取记录。这个 schema 驱动 Agent 用来读写和推理记录的技能文件。Schema 就是规格，生成的 skill 文件加上宿主机的 reconciler 是执行层。

跟任何好 harness 一样，schema 强制自己的不变量。谁声明一个 collection，无论 Agent 还是用户，在建模什么方面有广泛自由，但 loader 在使用之前就拒绝结构不连贯的 schema，一个 money 字段既没有字面量货币也没有 per-record 货币字段、一个 ref 指向不存在的 collection、一个 spawn 的后继出生时就已经匹配自己的条件导致无限重生、一个 triggerField 没有命名一个真正的 date 字段。每个失败都是一个精确、可操作的信息，作者不用人在环就能行动。

那些不该漂移的部分属于宿主机，每次运行完全一致，触发和清除铃铛的 reconciler、推进每次循环的公历日期运算、让 spawn 幂等的 create-if-absent 写入。Collection 在后续每次编辑中保持正确，靠的是 schema 不让不正确的通过。

新的动作在于谁写 DSL。在 SWE-agent 的案例里，工程师设计 harness，Agent 在里面运行。Collections 把 harness 的编写推给了最终用户，通过声明一个 schema，一个非工程师实际上在设计 Agent 将工作的环境。这是 harness 工程的字面民主化。"工程师设计环境而不是写代码"变成了"任何人都能声明式地设计环境，然后让 Agent 在里面执行"。

### Vibe Crafting，用户视角的名字

从用户椅子位置看，这种感觉有一个好名字，vibe crafting。"Vibe coding"让开发者通过描述意图、让有能力的模型填充代码来变出软件，vibe crafting 让最终用户以同样的方式变出一个可用的数据应用，一个 collection，当内置视图不够用时再加一个自定义视图来看到数据。"加一个优先级字段。""把这个做成看板跟踪。""让房租每月循环。""给我一个年度总览视图。"用户看不到 schema 或任何一行 HTML，他们描述想要什么，东西就出现了，活的。

很容易把这完全归功于模型，有代码能力的 LLM 是让这件事成为可能的原因。但可能不等于可以安全地交给读不懂输出的人。开发者 vibe coding 仍然会审查 diff、跑测试、出事了自己扛。最终用户没有这些，他们不能审计一个他们不知道存在的 schema，也不应该需要审计。填上这个差距的是 harness。Collection DSL 把能表达的东西约束到宿主机能安全渲染的范围，schema validator 在应用加载之前就拒绝一个不连贯的应用，附带一个 Agent 能在无人值守下行动的信息。自定义视图作为沙箱化的、能力受限的 HTML 运行，只能接触这一个 collection 的数据。每一道护栏都是一个非开发者能拿到 LLM 编码能力、但不必同时拿到它的失败模式的原因。

拿掉 harness，剩下的是一个未经训练的用户拿着一把上了膛的代码生成器。

## 唯一的危险，设计好逃生口

让 DSL 成为好 harness 的那份刚性，也是它的失败模式。当语言无法表达用户真正需要的东西时，Agent 会做两件坏事之一，放弃，或者把 DSL 扭曲成它从未打算承载的东西。一个太难的 DSL 变成了笼子。

设计良好的 DSL 都用同一种方式回答这个问题，提供一个通向更有表达力层级的明确出口。一个 collection 在记录需要表单无法捕获的人类判断时，退出它的声明式 schema 进入一个种好种的聊天，一个拥有完整工具的 Agent，它的 action 按钮就是启动这样一个聊天。Collection 的展示也有同样的出口，当宿主机渲染的字段类型无法好好展示数据时，schema 退出到一个自定义 HTML 视图，Agent 写任意代码、宿主机沙箱化地提供，而不是把字段类型的词汇扭曲成一个布局来承载它从未打算表达的东西。MulmoScript 可以引入任意外部资源而不是坚持一切都要用自己的原语来表达。

DSL-as-harness 的艺术在于选择约束在哪里生效，并在它不生效的地方提供一条干净的、可读的出路。一个没有逃生口的 harness 最终会强迫 Agent 要么失败要么撒谎，两者都比一个稍微泄漏的抽象更糟。

## 为什么模型越强，DSL 越重要

有一个诱人的直觉，DSL 是弱模型的拐杖，模型变聪明了就可以直接给它们通用代码、丢掉护栏。实际情况相反。DSL 的论证在你想自主委托、长期运行 Agent 的地方最强，没有人会审查每一步、输出必须是可验证的、执行必须是确定性的和可逆的。这些是严肃的 Agent 工作条件，而且随着我们信任 Agent 更多，它们变得更重要。

一个更聪明的模型在 DSL harness 里，是把能力指向真正需要判断的问题，说什么、构建什么、表达什么，而语言保证剩下的部分。模型是推理引擎。DSL 是决定它该推理什么的特别锋利的方式。把那个边界画对就是全部游戏，一个精心选择的 DSL 画得异常精确。
