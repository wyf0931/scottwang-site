课程设计者认为你对数学应该比较熟悉。因此，本单元以一个公式开头：
> 好的文档 = 目标读者完成任务所需的知识和技能 − 目标读者当前的知识和技能

换句话说，要确保你的文档提供读者需要但尚未拥有的信息。因此，本单元讲解如何做以下事情：

- 定义你的目标读者。
- 确定目标读者需要学什么。
- 让文档贴合目标读者。

## 定义你的目标读者

严肃的文档工作会花费大量时间和精力来定义目标读者。这些工作可能涉及问卷调查、用户体验研究、焦点小组和文档测试。你可能没有那么多时间，所以本单元采取一种更简单的方法。

先确定你的目标读者的**角色**。常见的角色包括：

- 软件工程师
- 非工程师的技术角色（例如技术项目经理）
- 科学家
- 科学领域的专业人士（例如医生）
- 本科工程专业学生
- 研究生工程专业学生
- 非技术岗位

我们很高兴地看到，许多非技术岗位的人拥有出色的技术和数学能力。然而，角色仍然是定义目标读者时一个重要的近似起点。同一角色内的人*通常*共享某些基础技能和知识。例如：

- 大多数软件工程师熟悉常见的排序算法、[大 O 表示法](https://en.wikipedia.org/wiki/Big_O_notation)以及至少一门编程语言。因此，你可以指望软件工程师懂得 O(n) 是什么意思，但不能指望非技术岗位的人懂 O(n)。
- 一份面向医生的研究报告，应该和同一份研究针对普通大众的报纸文章截然不同。
- 一位教授向研究生解释新的机器学习方法，应该与向本科一年级学生解释时不同。

如果同一角色内的人共享完全相同的知识，写作就会轻松得多。不幸的是，同一角色内的知识很快就会分化。Amal 是 Python 专家，Sharon 擅长 C++，Micah 擅长 Java。Kara 喜欢 Linux，但 David 只懂 iOS。

单靠角色不足以定义目标读者。也就是说，你还必须考虑目标读者与知识的*距离*。Frombus 项目的软件工程师了解一些相关的 Dingus 项目，但对无关的 Carambola 项目一无所知。平均而言，心脏病专家对耳朵问题的了解比普通软件工程师多，但远不如听力学家。

时间也会影响这种距离。例如，几乎所有软件工程师都学过微积分。然而，大多数软件工程师在工作中不用微积分，所以他们关于微积分的知识会逐渐淡忘。反过来，经验丰富的工程师通常比同一项目的新工程师对自己的项目了解得多得多。

### 目标读者分析示例

下面是对虚构项目 Zylmon 的一个目标读者分析示例：
> 项目 Zylmon 的目标读者属于以下角色：
>
> - 软件工程师
> - 技术产品经理
>
> 目标读者与知识的距离如下：
>
> - 我的目标读者已经知道 Zyljeune API，它与 Zylmon API 有些相似。
> - 我的目标读者懂 C++，但通常没有在新的 Winged Victory 开发环境中构建过 C++ 程序。
> - 我的目标读者在大学学过线性代数，但团队中很多人需要复习矩阵乘法。

## 确定目标读者需要学什么

写下目标读者为达成目标需要学习的全部内容清单。在某些情况下，这个清单应该包含目标读者需要*执行*的任务。例如：
> 读完文档后，读者将知道如何做以下事情：
> - 使用 Zylmon API 按价格列出酒店。
> - 使用 Zylmon API 按位置列出酒店。
> - 使用 Zylmon API 按用户评分列出酒店。

注意，目标读者有时必须按一定顺序掌握任务。例如，你的目标读者可能需要先学习如何在一个新的开发环境中构建并执行程序，*然后*才能学习如何编写特定类型的程序。

如果你在写设计规格说明，那么你的清单应该聚焦于目标读者应该学习的信息，而不是掌握特定任务。例如：
> 读完设计规格说明后，读者将学到以下内容：
> - Zylmon 优于 Zyljeune 的三个原因。
> - Zylmon 为何消耗了 5.25 个工程年进行开发的五个原因。

## 让文档贴合目标读者

为满足目标读者的需求而写作，需要无私的同理心。你必须创造出满足读者好奇心的解释，而不是满足你自己的好奇心。你如何走出自我，让文档贴合目标读者？遗憾的是，我们没有简单的答案。不过，我们可以提供几个值得关注的参数。

### 词汇与概念

让你的词汇匹配目标读者。参见[用词](https://developers.google.com/tech-writing/one/words)了解详情。

注意距离。你团队里的人可能懂你们团队的缩写，但其他团队的人懂这些缩写吗？随着目标读者范围变广，你要假设自己需要解释更多内容。

同样，你软件团队里经验丰富的人可能懂你们团队项目的实现细节和数据结构，但几乎其他所有人（包括团队新成员）都不懂。除非你专门为团队里其他经验丰富的成员写作，否则通常你需要解释的内容比你预想的多。

### 知识的诅咒

专家常常遭受**知识的诅咒**，意思是他们对一个主题的专家级理解会破坏他们向新手做出的解释。作为专家，很容易忘记新手不知道你已经知道的东西。新手可能无法理解那些对微妙交互和深层系统的旁涉性解释，而专家并不会停下来解释这些。

从新手的角度看，知识的诅咒就像是因为一个尚未编译的模块而出现的"找不到文件"链接错误。

### 练习

1. 假设下面这段文字是一篇面向从未编程过的医生的论文的开头。找出这段文字中受知识诅咒影响的方面：

   > C 是一门中级语言，比汇编语言高，但比 Python 和 Java 低。C 语言为程序员提供了对程序所有方面的精细控制。例如，使用 C 标准库，分配和释放内存块很容易。在 C 中，直接操作指针是司空见惯的事。
2. 假设前面这段文字是面向刚接触 C、但熟悉 Python 的计算机科学本科生的。这段文字还受知识的诅咒影响吗？

#### 点击图标查看答案。

1. 这段文字深受知识的诅咒影响。目标读者从未编程过，所以以下术语不合适或不熟悉：
   - 语言
   - 中级语言
   - 汇编语言
   - Python
   - Java
   - 程序
   - C 标准库
   - 分配和释放内存块
   - 指针
2. 对于另一种目标读者，这段文字也受知识的诅咒影响。普通的 Python 程序员不了解操作内存或指针。更好的开头段落应该是把 C 和 Python 进行比较和对比。

### 简单的词

英语已成为全球技术交流的主导语言。然而，相当大比例的技术读者更习惯英语之外的语言。因此，优先使用简单的词而不是复杂的词；避免使用过时或过于复杂的英语单词。[长词癖](https://www.google.com/search?q=sesquipedalian)和生僻词会赶走一些读者。

### 文化中立与习语

让你的写作保持文化中立。不要让读者为了理解软件如何工作而去了解 NASCAR、板球或相扑的来龙去脉。例如，下面这句话——满是美国馅饼般美国化的棒球隐喻——可能会让一些巴黎读者感到困惑：
> 如果说 Frambus 5.0 是一记扎实的一垒安打，那么 Frambus 6.0 就是一记站上二垒的二垒安打。

**习语**是指整体含义与组成该短语的各个单词字面含义不同的短语。例如，下面这些短语都是习语：

- a piece of cake（小菜一碟）
- Bob's your uncle（一切就绪）

蛋糕？Bob？大多数美国读者认识第一个习语；大多数英国读者认识第二个习语。如果你专门为英国读者写作，那么 *Bob's your uncle* 没问题。但如果你为国际读者写作，就用 *this task is done*（这事就办好了）来替换这个习语。

习语在我们的语言中根深蒂固，以至于习语特殊的非字面含义对我们来说变得不可见。也就是说，习语是知识诅咒的另一种形式。

注意，你的一些读者会使用翻译软件来阅读你的文档。翻译软件在面对文化典故和习语时，往往比面对朴实简单的英语更吃力。

### 练习

找出下面这些句子的问题：

1. 从 3.0 版本开始，调用 Frambus 方法仍然是 kosher 的。
2. 决定哪些 BlogResource 约束是可组合的，是一个 sticky wicket。
3. 话虽如此，你还是得写单元测试。

#### 点击图标查看答案。

1. 在世界上一些地方，**kosher** 已经成为"可接受用法"的俚语。然而，许多读者会疑惑宗教饮食法规和软件有什么关系。
2. **sticky wicket** 是英国俚语，不容易传播。用**棘手的问题**这个短语来替换就能解决这个问题。
3. **Be that as it may** 是一个习语。用**不过**这个过渡词替换就能解决这个问题。
