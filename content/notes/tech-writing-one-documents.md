你能写句子。你能写段落。但你能把所有段落组织成一份连贯的文档吗？

## 说明文档的范围

一份好文档从定义范围开始。例如：
> 本文档描述项目 Frambus 的设计。

一份更好的文档还会定义它的非范围——也就是目标读者可能合理期望文档覆盖、但实际没有覆盖的主题。例如：
> 本文档不描述相关技术项目 Froobus 的设计。

范围和非范围声明不仅让读者受益，也让作者（你）受益。写作时，如果你的文档内容偏离了范围声明（或者*进入*了非范围声明），那么你要么把文档重新聚焦，要么修改范围声明。审阅初稿时，删除任何无助于满足范围声明的章节。

### 练习

下面这段文字有什么问题？
> 本文档解释如何使用 Frambus API 创建、更新和发布 Fwidget。本文档不解释如何使用 Frambus API 删除 Fwidget，也不涵盖 Linux 操作系统的历史。

非范围应该只包含用户会合理期望文档覆盖的信息。没有哪个合理的用户会期望文档覆盖 Linux 操作系统的历史。

## 说明目标读者

一份好文档会明确说明它的目标读者。例如：
> 本文档面向以下读者：
>
> - 软件工程师
> - 项目经理

除了目标读者的角色，一份好的读者声明还可能说明任何先决知识或经验。例如：
> 本文档假设你理解矩阵乘法和反向传播的基础知识。

在某些情况下，读者声明还应该说明先决阅读或课程。例如：
> 在阅读本文档之前，你必须先阅读《项目 Froobus：新的希望》。

## 在开头总结要点

工程师和科学家是大忙人，不一定会读完你文档的全部 76 页。想象你的同事可能只读你文档的第一段。因此，要确保文档的开头回答了读者最关心的问题。

专业写作者会投入大量精力在第一页上，以提高读者读到第二页的几率。然而，任何长文档的开头都是最难写的一页。做好反复修改第一页的准备。

### 对比与对照

在你的职业生涯中，无论你多么有创造力，你都只会写出极少数真正包含革命性想法的文档。你的大部分工作都是演化性的，建立在此前的技术和概念之上。因此，把你自己的想法与目标读者已经理解的概念进行对比和对照。例如：
> 这个新应用与 Frambus 应用相似，只是图形效果要好得多。

或者：
> Froobus API 处理与 Frambus API 相同的用例，只是 Froobus API 更容易使用。

### 练习

下面这个引言有什么问题？
> Frambus 天气应用 v2 引入了 v1 所没有的十个新功能。最重要的是，v2 提供两周预报，而 v1 只提供一周预报。潮汐信息不会改变。

#### 点击图标查看答案。

最后一句话（关于潮汐的）不够重要，不值得出现在开头段落里。第一句话提到了十个新功能，所以读者很可能会期待听到更多关于这些新功能的内容。结果，最后一句话指的不是新功能，而是别的东西。

## 为目标读者写作

本课程反复强调定义目标读者的重要性。在本节，我们聚焦于把目标读者定义作为组织文档的一种手段。

### 定义目标读者的需求

回答以下问题有助于你确定文档应该包含什么：

- 你的目标读者是谁？
- 你的目标读者的目标是什么？他们为什么读这份文档？
- 你的读者在阅读文档*之前*已经知道什么？
- 你的读者在阅读文档*之后*应该知道什么或能做什么？

例如，假设你发明了一种新的排序算法，它和快速排序相似。下面这个列表包含对前面问题的一些可能的回答：

- **你的目标读者是谁？** 目标读者包括我所在组织里所有的软件工程师。
- **你的目标读者的目标是什么？** 我的目标读者想找到更高效的排序数据的方法。他们读这份文档是为了判断这个新算法是否值得实现。
- **你的读者在阅读文档*之前*已经知道什么？** 我的目标读者知道如何写代码，并且以前学过排序算法，包括快速排序。然而，我的目标读者中大多数人都好几年没有实现或评估过排序算法了。
- **你的读者在阅读文档*之后*应该知道什么或能做什么？** 我的目标读者将能做以下所有事情：
  - 理解这个算法与快速排序的对比和对照。
  - 识别这个算法优于快速排序算法的两类数据集。
  - 用他们选择的编程语言实现这个算法。
  - 识别这个算法表现不佳的两个边界情况。

### 组织文档以满足目标读者的需求

定义目标读者的需求后，组织文档以帮助读者获得他们需要的信息。例如，根据上一节的回答，文档的大纲可以如下所示：

1. 算法概览
   - 与快速排序的对比和对照，包括大 O 比较
     - 链接到关于快速排序的维基百科文章
   - 适合该算法的最佳数据集
2. 实现算法
   - 用伪代码实现
   - 实现技巧，包括常见错误
3. 算法的深入分析
   - 边界情况
   - 已知的未知
