像 [Gemini](https://gemini.google.com) 这样的[**大语言模型**](https://developers.google.com/machine-learning/glossary#large-language-model)（**LLM**）可以帮助你改进文档。另一方面，粗心大意地使用 LLM 可能给你的文档注入错误。本节聚焦如何负责任地使用 LLM，以帮助你完成以下任务：

- 生成初稿。
- 修改文档。
- 格式化文档。
- 总结文档。

你向 LLM 发出的请求称为 [**提示（prompt）**](https://developers.google.com/machine-learning/glossary#prompt)。LLM 通过生成 [**响应（response）**](https://developers.google.com/machine-learning/glossary#response) 来回应提示。本模块解释如何编写能产生有用响应的提示。

总的来说，写出好的提示需要遵循好的技术写作原则。

> [!CAUTION]
> **注意：** 响应有时会包含错误。务必仔细检查响应，不仅检查事实错误，也要检查响应"感觉"不对的地方。

## 生成初稿

LLM 可以帮助你写出那份让人抓狂、恨不得撞墙的初稿。要得到一份好的初稿，你需要提供好的提示。

LLM 对它们"了解"的主题生成最佳响应。LLM 了解以下内容：

- LLM [**预训练**](https://developers.google.com/machine-learning/glossary#pre-training) 时所基于的信息。
- LLM 随后 [**微调**](https://developers.google.com/machine-learning/glossary#fine-tuning) 所基于的任何额外信息。
- 传统上通过搜索引擎可获得的信息（如果 LLM 通过 [检索增强生成（RAG）](https://developers.google.com/machine-learning/glossary#retrieval-augmented_generation) 得到增强）。
- 你在提示或附件中提供的任何额外信息。

例如，大多数 LLM 都基于大量关于 Python 编程语言的信息进行了预训练。因此，大多数 LLM 都能生成关于任何标准 Python 函数的初稿文字。然而，除非你在提示中传入你今早编写的那个 Python 函数的源代码，否则 LLM 并不知道它。

本节的其余部分将探讨为生成初稿而编写有效提示的具体方式。

### 扮演一个角色

当提示告诉 LLM 扮演一个角色时，LLM 往往能生成更好的响应。例如：

推荐
> 你是一位技术写作专家……
> 你是一位耐心的高级软件工程师，正在和一位初级软件工程师交谈……
> 你是一位计算机科学教授，正在为一年级学生编写幻灯片……

要选择角色，请想象谁最能向目标读者解释或教授某个主题。

### 确定目标读者

提示应该指明目标读者。例如，下面的提示*没有*指明目标读者，所以 LLM 的响应可能有帮助也可能没有：

不推荐
> 描述 Carambola 应用。

相比之下，下面的提示要具体得多，很可能会产生更好的响应：

推荐
> 向团队中负责维护该应用的新员工描述 Carambola 应用。
> 向另一个团队的软件工程师描述 Carambola 应用……
> 向市场副总裁描述 Carambola 应用……

### 指明文档类型

你想要 LLM 生成什么*类型*的文档？例如，下面的提示没有回答上面这个问题：

不推荐
> 生成一份文档……

相比之下，下面的提示更具体：

推荐
> 生成一份 FAQ……
> 生成一封电子邮件……

考虑提示生成一份冗长文档的一个子集，而不是整份文档。例如，如果一份程序员指南需要几百页长，那么下面的提示可能产生糟糕的响应：

不推荐
> 生成一份关于……的完整程序员指南

相比之下，提示生成具体的章节可能会产生更好的响应：

推荐
> 生成程序员指南中解释如何预订的那一节。
> 生成程序员指南中解释如何更改预订的那一节。

### 界定文档的目标

人们阅读技术文档是为了学点什么或做点什么。好的提示会告诉 LLM 读者打算用这些信息做什么。例如，下面的提示提供了实际的目标：

推荐
> 读完 FAQ 后，读者应该能够自己调试常见问题。
> 读完本教程后，读者应该知道 Python 中普通函数与 lambda 函数的区别。

### 选择风格

LLM 的响应通常是一大堆无序列表，由短段落连接起来。这通常是技术写作的合适风格。不过，你的提示可以建议一种不同的风格或格式。例如：

推荐
> ……按以下顺序组织发布说明：
>
> 1. 一段引言
> 2. 一个包含每个 bug 一行摘要的表格
> 3. 每个 bug 的子节，详述问题与任何规避方法

另外，如果你喜欢另一份文档的风格，你可以把那份文档附加到提示中，告诉 LLM 模仿它的风格（或其风格的选定方面）。你甚至可以指定要模仿的风格指南。例如：

推荐
> 为下面这个 Python 函数编写符合 Google Python 风格指南的注释。

LLM 的响应往往太长。考虑告诉 LLM 缩短响应。例如：

推荐
> ……把无序列表限制为最重要的三项。

> **注意：** LLM 有时会犯数学错误，所以生成的无序列表可能并不恰好包含三项。

### 添加提示约束

你可以通过在提示中添加具体约束来减少 LLM 响应中的[幻觉](https://developers.google.com/machine-learning/glossary#hallucination)。例如，你可以约束 LLM 只使用你在提示中提供的信息：

推荐
> 在你的响应中只使用以下文字中的信息：

你也可以约束 LLM 只使用一组特定文件中的信息。

### 迭代与精炼

你最初的提示通常不会产生完美的响应。你可能需要多次提示，每次都做调整。如果响应仍然不太好，请考虑以下问题：

- 你的提示是否指明了角色、目标读者和文档类型？
- 你的提示是否足够具体？你是否恰好请求了你想要的东西？
- 你的提示是否清晰？你的提示是否符合 [技术写作（一）](https://developers.google.com/tech-writing/one) 中的技术写作课程要点？如果你把同样的提示给一个人类，那个人会知道你在请求什么吗？

有时候，完美是好的敌人。如果一份响应非常好但还不算完美，继续精炼提示是很诱人的。然而，与其没完没了地精炼提示，不如自己编辑那份很好的响应，这样往往更高效。

> **注意：** LLM 对*相同*的提示常常产生不同的响应。所以，即使重新发出相同的提示，有时也算一种迭代。

### 设定上下文

如前所述，LLM 只能使用它们可用的信息源。提供额外信息来建立上下文，有助于 LLM 生成更好的响应。这些额外信息几乎可以是与主题相关的任何信息，包括：

- 文档
- 会议记录
- 源代码
- 电子邮件
- 示意图

例如，把相关的源代码附加到提示中，可以帮助 LLM 生成文档的初稿：

推荐
> 基于附加的源代码来写文档。

LLM 通常假定附件中的信息是事实，这可能会引发问题。例如，LLM 可能会错误地假定附加源代码中的 bug 实际上是功能。

### 考虑这个反面观点

当你依赖 LLM 来创作初稿时，你失去了写作过程的*益处*。
> "一个人写作是为了知道自己正在想什么。"——Abraham Verghese

写作是一种挣扎，但这种挣扎会把想法结晶化，把模糊的念头变成清晰的计划。在你写出设计文档之前，你还没有完整地梳理过所有问题及其解决方案。清晰的技术写作是清晰技术思维的副产品。

### 练习

一个设计团队记录了一场旨在设计一款新应用的头脑风暴会议。我们捕获了那场极具创造力的会议的[记录](https://developers.google.com/tech-writing/two/artifacts/design-meeting-transcript)。请提示 LLM 根据记录创建一封电子邮件。这封邮件应该旨在说服工程副总裁资助开发这款宠物翻译应用。副总裁很忙，所以请保持邮件简短而聚焦。

#### 点击图标查看一种可能的答案。

提示几乎从来不会有唯一正确答案。话虽如此，这里有一种可能的提示：
> 你是一位高级工程师。根据记录，写一封邮件，说服工程副总裁资助开发宠物翻译应用。语气要严肃、正式。工程副总裁很忙，所以保持邮件简短。以一段概述提案的开头段落开始。然后提供一个三项无序列表。最后以一句话的行动号召结束。

## 修改文档

LLM 擅长批判性分析。LLM 是如此出色的评论家，以至于它们甚至能发现*它们自己*生成的文本中的错误。

### 重组

我们建议先修复组织问题，再编辑语法和风格问题。当提示 LLM 重组文档时，清晰详细的提示会胜过含糊的提示。例如，下面的提示迫使 LLM 去猜测你的意图：

不推荐
> 重组附加的课程。

相比之下，下面的提示提供了语境和具体性，帮助引导 LLM 更有效地重组。

推荐
> 附加的课程是机器学习中逻辑回归的入门。课程面向能编写 Python 但几乎不了解机器学习基础的二年级计算机科学学生。你能推荐一种更好的课程模块组织吗？例如，我应该把哪些材料移到另一个模块？课程是否应该更早讨论分类阈值？

### 文字编辑

LLM 对语法、标点和拼写"知道"得非常多。所以，像下面这样的一般性提示通常能发现令人尴尬的错误：

推荐
> 找出附加段落中的语法、标点和拼写问题。

### 发现风格问题

LLM 可以发现风格问题。例如：

推荐
> 识别下面段落中的任何被动语态：

更进一步，你可以让 LLM 建议修改。例如：

推荐
> 把下面段落中的任何被动语态句子替换为它们的主动语态等价句。

你可以让 LLM 对风格问题进行一次全面排查：

推荐
> 附加文档在哪些方面偏离了 Google 技术写作（一）课程的写作原则？假设文档面向想要在测试自动化上精进的专业软件工程师。

### 发现其他问题

LLM 还擅长发现文档中的逻辑不一致或明显错误。在提示中提供一个角色，可以帮助 LLM 进入正确的"思维模式"。例如：

推荐
> 你是一位计算机科学教授，正在审阅一份描述新机器翻译范式研究的论文初稿。检查引言部分中关于先前算法描述的任何错误。然后评估论文其余部分是否存在任何可能的逻辑缺陷。

## 格式化文档

LLM 可以把文档从一种格式转换为另一种。例如，你可以让 LLM 把 Word 文档转换为 HTML 或 Markdown。要做到这一点，你需要提供：

- 要转换的文档。
- 目标格式。
- 任何具体的格式要求。

例如：

推荐
> 把附加的 Word 文档转换为 Markdown，把所有标题设为二级或三级。

你也可以让 LLM 重新格式化一份文档以符合特定的风格指南。例如：

推荐
> 重新格式化附加的 HTML 文档，使其符合 Google 开发者文档风格指南。

## 总结文档

把冗长的文字压缩到 50 或 100 词，是如此困难，以至于大多数技术专业人士都难以写出摘要、执行摘要和概览。幸运的是，LLM 通常擅长总结。总结文本的提示通常应指明：

- 风格
- 目标读者
- 目的
- 可选地，语气

例如，这里有一个好的总结提示：

推荐
> 为附加课程写一句总结。把总结指向会用总结来决定是否选课的软件工程师。让总结有吸引力又专业；总结看起来不应该是营销材料。

讽刺的是，一个好的总结提示可能比生成的总结还要长。

在某些情况下，总结必须符合特定的风格。因此，你的提示应该指明或附加相关的风格指南。

在其他情况下，虽然风格没有在风格指南中成文，你的总结仍应类似于某些总结。你可以把那些典范总结作为提示的一部分传入。（这种技巧称为 [少样本提示（few-shot prompting）](https://developers.google.com/machine-learning/glossary/#few-shot-prompting)。）例如：

推荐
> 为附加的设计文档写一份 tldr 风格的总结，风格要匹配以下 tldr 总结：这门有趣的四小时课程为软件工程师打下 Python 的坚实基础。这门实践性的两小时课程引导软件工程师构建更好的提示来生成 Python 代码。

### 总结的替代媒介

如果你所处的媒介*需要*文字总结，那么你需要提供文字。不过有时，技术人士默认会产出文字总结，而非文字总结（例如图像或视频）可能更令人难忘或更有吸引力。

或者，换一种角度看问题，你可以让 LLM 为一幅图像写文字总结。

### 练习

我们捕获了[这场](https://developers.google.com/tech-writing/two/artifacts/design-meeting-transcript)为设计一款新应用而进行的极具创意的头脑风暴会议的记录。

**任务 1：** 提示你最爱的 LLM 为头脑风暴会议中讨论的宠物翻译应用生成一句总结。（把记录与提示一起复制粘贴。）这句总结应该让其他工程师对参与这个项目产生兴趣。

#### 点击图标查看一种可能的答案。

一如既往，许多不同的提示都会产生好的响应。
这里有一种可能的提示：
> 你是一位受人尊敬的高级工程师。为附加记录中讨论的附加应用生成一句总结。把总结指向初级工程师。总结应该让那些初级工程师对参与这个项目产生兴趣。

**任务 2：** 提示你最爱的 LLM 创建一幅代表该应用的图像。图像应该帮助非技术人员理解这个应用。

#### 点击图标查看一种可能的答案。

这里有一种可能：创建一幅帮助非技术人员理解这个应用的图像。
