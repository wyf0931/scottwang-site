软件工程师通常尽量把实现代码的行数压到最少，原因如下：

- 更短的代码通常更容易被别人读懂。
- 更短的代码通常比更长的代码更容易维护。
- 多出来的代码行会引入额外的故障点。

事实上，同样的规则也适用于技术写作：

- 更短的文档读起来比更长的文档更快。
- 更短的文档通常比更长的文档更容易维护。
- 多出来的文档行会引入额外的故障点。

找到最短的文档实现需要花时间，但最终是值得的。短句比长句更有表现力，而且短句通常比长句更容易理解。

## 让每句话只聚焦一个想法

让每句话只聚焦一个想法、一个念头或一个概念。就像程序里的语句只执行一个任务一样，句子也应该只执行一个想法。例如，下面这句非常长的句子包含了多个想法：

> 20 世纪 50 年代末是编程语言的关键时期，因为 IBM 于 1957 年推出了 Fortran，次年 John McCarthy 推出了 Lisp，这给了程序员一种迭代式和一种递归式的问题求解方式。

把长句拆成一系列单想法句子，结果如下：

> 20 世纪 50 年代末是编程语言的关键时期。
> IBM 于 1957 年推出了 Fortran。John McCarthy 于次年发明了 Lisp。
> 因此，到 20 世纪 50 年代末，程序员已经可以用迭代或递归的方式求解问题。

### 练习

把下面这句过长的句子转换成一系列更短的句子。不要改动太多；只需把它从一句话拆成几句话。

> 在 bash 中，使用 if、then 和 fi 语句来实现一个简单的条件分支块，其中 if 语句求值一个表达式，then 语句引入一个在 if 表达式为真时要运行的语句块，fi 语句标记条件分支块的结束。

## 把一些长句转换成列表

很多长技术句子里都藏着一个渴望挣脱的列表。例如，考虑下面这句话：

> 要改变循环的常规流程，你可以使用 **break** 语句（它把你跳出当前循环）或 **continue** 语句（它跳过当前循环当前迭代的剩余部分）。

当你在长句里看到连词 **or** 时，考虑把它重构成一个无序列表。当你在长句里看到嵌入的条目或任务列表时，考虑把它重构成一个无序或有序列表。例如，上面的例子含有连词 **or**，所以让我们把那个长句转换成下面的无序列表：

要改变循环的常规流程，调用以下语句之一：

- `break`，它把你跳出当前循环。
- `continue`，它跳过当前循环当前迭代的剩余部分。

### 练习

把下面这些句子重构得更短、更清晰。确保你的答案里包含一个列表：

1. 要开始使用 Frambus 应用，你必须先在合适的商店找到它，用有效的信用卡或借记卡付款，下载它，通过在 `/etc/Frambus` 文件中给 `Foo` 变量赋值来配置它，然后念两遍魔咒来运行它。

## 删除或精简多余词语

许多句子里含有填充词——占据空间却不滋养读者的"文字垃圾食品"。例如，看看你能不能在这句话里找出多余的词：

> 大于 100 的输入值会导致日志的触发。

把 **causes the triggering of** 替换成短得多的动词 **triggers**，就得到更短的句子：

> 大于 100 的输入值会触发日志。

多加练习后，你会一眼认出多余词语，并在删除或精简它们时感到巨大的快乐。例如，考虑下面这句话：

> 这份设计文档对 Frambus 项目进行了详细描述。

短语 **provides a detailed description of** 可以简化成动词 **describes**（或动词 **details**），所以结果句子可以变成：

> 这份设计文档描述了 Frambus 项目。

下表为一些常见的臃肿短语给出了替换建议：

| 臃肿 | 简洁 |
|---|---|
| 在当前这个时间点 | 现在 |
| 确定……的位置 | 找到 |
| 能够 | 可以 |

1. 尽管 Arnold 写的代码有 bug，他写的文档却无错。

3. 确定 Rikona 是否能够用 COBOL 写代码。
4. Frambus 导致 bug 的产生，这些 bug 将由 LogGenerator 方法记录到日志中。

## 减少从句（选学）

**从句**是一个独立的逻辑片段，包含一个动作者和一个动作。每个句子都包含以下内容：

- 一个主句
- 零个或多个从句

从句修饰主句中的想法。顾名思义，从句不如主句重要。例如，考虑下面这句话：

> Python 是一种解释型编程语言，它发明于 1991 年。
>
> - 主句：Python 是一种解释型编程语言
> - 从句：它发明于 1991 年

通常可以通过引导从句的词来辨认从句。下面的列表（远非完整）列出了常见的引导从句的词：

- which
- that
- because
- whose
- until
- unless
- since

有些从句以逗号开头，有些则没有。例如，下面这句话中高亮的从句以 **because** 开头，且不含逗号：

> 我更喜欢用 C++ 编程，因为我喜欢强类型。

编辑时，要仔细审视从句。牢记"一句话 = 一个想法"和[单一职责原则](https://en.wikipedia.org/wiki/Single-responsibility_principle)。句中的从句是在*扩展*那个单一想法，还是*岔开*成了另一个想法？如果是后者，考虑把那些碍事的从句拆成独立的句子。

### 练习

判断下面哪些句子含有应该被岔开成独立句子的从句。（不要改写句子，只识别出应该改写的句子。）

1. Python 是一种解释型语言，这意味着该语言可以直接执行源代码。
2. Bash 是一种现代 shell 脚本语言，它从 KornShell 88 吸收了很多特性，而 KornShell 88 是在贝尔实验室开发的。
3. Lisp 是一种依赖波兰前缀记法的编程语言，而波兰前缀记法是波兰逻辑学家 Jan Łukasiewicz 发明的系统之一。
4. 我不想说 Fortran 很老，但只有放射性碳定年才能确定它的真实年龄。

#### 点击图标查看答案。

我们给从句加了底色。

1. Python 是一种解释型语言，这意味着该语言可以直接执行源代码。**这句话里的从句扩展了主想法，所以这句话保持原样即可。**
2. Bash 是一种现代 shell 脚本语言，它从 KornShell 88 吸收了很多特性，而 KornShell 88 是在贝尔实验室开发的。**第一个从句扩展了主想法，但第二个从句拐向了另一个方向。把这句话拆成两句。**
3. Lisp 是一种依赖波兰前缀记法的编程语言，而波兰前缀记法是波兰逻辑学家 Jan Łukasiewicz 发明的系统之一。**第一个从句对句子很关键，但第二个从句把读者带得离主句太远。把这句话拆成两句。**
4. 我不想说 Fortran 很老，但只有放射性碳定年才能确定它的真实年龄。**从句对句子很关键，所以这句话保持原样即可。**

## 区分 that 与 which

**that** 和 **which** 都引导从句。它们有什么区别？嗯，在一些国家，这两个词几乎可以互换。但不可避免地，来自美国的敏锐读者会愤怒地宣布你又把这两个词搞混了。

在美国，把 **which** 留给非必需的从句，用 **that** 表示句子离不开的关键从句。例如，下面这句话的关键信息是"Python 是一种解释型语言"，句子可以没有 *Guido van Rossum invented*：

> Python 是一种解释型语言，**which** Guido van Rossum invented。

相比之下，下面这句话需要 *don't involve linear algebra*：

> Fortran 是适合数学计算的完美选择，**that** don't involve linear algebra。

如果你大声读一句话，在从句前听到一个停顿，就用 **which**。如果没听到停顿，就用 **that**。回去读上面两个例句。你在第一句里听到停顿了吗？

在 **which** 前加逗号；不要在 **that** 前加逗号。
