# GitHub 项目卡片与选型文章设计

## 状态

已确认方向，等待实现前复核。

## 背景

站点已经支持在文章 frontmatter 中声明 `github: "owner/repo"`，构建时会读取 GitHub 元数据，并在文章底部渲染一个简单的仓库链接卡片。现有卡片信息密度低、视觉权重弱，读者很难把它识别为文章介绍的核心项目。

GitHub 项目分享也需要稳定的文章结构。文章面向架构师和技术选型读者，重点应当落在业务背景、工程问题、解决路径、替代方案和选择边界上。文章不应退化为 README 摘要或功能清单。

## 目标

- 提供一个可以在 MDX 正文任意位置插入的 GitHub 项目卡片。
- 让卡片具有清晰的 GitHub 识别、项目身份、关键指标和外链入口。
- 保留构建时 GitHub 元数据缓存与离线 fallback。
- 取消文章详情页自动追加到底部的 GitHub 卡片，避免位置不可控和重复展示。
- 为 GitHub 项目分享建立统一、业务导向、适合架构选型的文章框架。
- 第一篇文章使用 `lexiforest/curl_cffi`，并在文章正文中显式插入卡片。

## 非目标

- 不引入 GitHub 运行时 API 请求。
- 不把 GitHub 项目变成独立 CMS 内容类型。
- 不为每个项目设计一套完全不同的文章模板。
- 不把文章写成完整 API 文档、项目宣传稿或未经验证的亲身评测。

## 方案决策

采用正文内嵌的 MDX 组件：

```mdx
<GithubRepoCard repo="lexiforest/curl_cffi" />
```

组件可以出现在文章开头、核心能力之后、替代方案之后或资源部分。文章作者决定它出现的位置，页面布局不再自动把卡片强行放在评论前。

`github` frontmatter 字段暂时保留，用于兼容旧内容和构建缓存。它不再触发详情页自动渲染。构建脚本需要同时扫描 frontmatter 与 `GithubRepoCard` 的 `repo` 属性，确保显式组件使用的仓库也能获得缓存数据。

## GitHub 卡片设计

卡片作为正文中的技术资料模块，至少包含：

- GitHub 标识或清晰的 GitHub 图形标记，不使用难以识别的 `GH` 占位文字。
- 仓库所属者和仓库名称，例如 `lexiforest/curl_cffi`。
- GitHub 返回的项目描述，缺少描述时使用简短 fallback。
- Stars、Forks、主要语言和更新时间等关键元数据。
- 明确的 `View on GitHub` 外链按钮或链接。
- 可用时展示仓库 owner avatar，并为图片提供可访问的替代文本。

视觉方向保持站点的克制和技术感，但提高卡片的识别度：更强的边界、足够的对比度、明确的标题层级、可扫描的统计信息和清晰的 hover/focus 状态。卡片应当在浅色和深色主题、窄屏和键盘操作下都可用。

组件由仓库 slug 获取缓存数据，缓存缺失或 GitHub API 不可用时仍展示可点击的仓库链接和基础 slug 信息。组件不应因为元数据缺失而阻断文章构建。

## GitHub 项目文章框架

文章类型继续使用现有的资源内容模型，通常放在 `content/notes/<slug>/index.md` 或 `.mdx`：

```yaml
title: "项目名：面向某个工程问题的解决方案"
description: "从业务背景、技术路径和选型边界介绍项目。"
date: "2026-08-16"
type: "notes"
kind: "resource"
resourceType: "github"
resourceUrl: "https://github.com/owner/repo"
github: "owner/repo"
tags: ["GitHub", "Python"]
draft: true
```

正文按材料调整，不要求每篇都写满所有章节。推荐顺序如下：

1. **项目速览**
   - 一句话说明项目解决什么问题。
   - 适合什么场景，不适合什么场景。
   - 给出当前判断和读者是否值得继续读。

2. **背景与问题**
   - 业务或工程上下文是什么。
   - 旧方案在哪一步失效。
   - 失败带来的成本、风险或交付影响是什么。

3. **解决思路**
   - 项目选择了什么技术路径。
   - 核心抽象是什么。
   - 一次请求、任务或数据处理流程如何完成。

4. **核心能力**
   - 按真实功能模块展开。
   - 对浅项目，重点写模块、输入输出和使用方式。
   - 对复杂项目，重点写任务流、数据流、状态边界和失败处理。

5. **技术栈与架构**
   - 语言、运行时、依赖、协议、存储和部署方式。
   - 解释关键技术选择带来的收益与代价。

6. **同类项目比较**
   - 选择两到四个有代表性的替代项目。
   - 比较能力、性能、兼容性、维护成本和适用边界。
   - 不把项目 README 的自我描述直接写成结论。

7. **适用场景与选型建议**
   - 谁适合采用，谁不应采用。
   - 团队规模、部署环境、合规要求和运维能力会怎样影响选择。
   - 明确当前材料能支持的判断范围。

8. **快速上手**
   - 提供一段能验证核心价值的最小示例。
   - 写明版本、运行条件和最容易遇到的限制。

9. **项目资料**
   - 在合适的位置插入 `GithubRepoCard`。
   - 只保留读者下一步需要的官方文档、License、Release 或示例链接。

### 材料与写作边界

- 项目能力、版本、License、性能数据和兼容性必须以官方仓库、官方文档、源码或可核验测试为依据。
- 只有官方资料时，写资料解读或选型分析，不伪装成亲身体验。
- 将官方自述、作者分析、实际测试和推断分开处理。
- 文章完成初稿后，必须使用 `human-writing` skill 做事实边界、段落推进、句子节奏和 AI 痕迹审查。
- 文章不使用重复的“优势、价值、未来展望”段落凑长度，也不使用商业黑话替代具体流程、成本和责任。

## 第一篇文章

第一篇选题为 `curl_cffi`。官方仓库说明它是通过 CFFI 绑定 curl-impersonate 的 Python HTTP 客户端，支持浏览器 TLS/JA3 与 HTTP/2 指纹模拟，并提供 requests-like API、异步请求、代理、WebSocket 和 HTTP/3 能力。文章应重点讨论这些能力对应的实际工程问题，并与 `requests`、`httpx`、`aiohttp`、`pycurl` 等项目比较，而不是只罗列功能。

文章应补充安全与合规边界：TLS 指纹模拟不能等同于绕过所有风控或反爬机制，使用时需要遵守目标站点条款和适用法律。

`content/notes/human-writing-skill.md` 迁移为正文显式插入：

```mdx
<GithubRepoCard repo="KKKKhaziz/human-writing" />
```

并删除文末重复的 `human-writing GitHub 仓库` 与 `human-writing Release` 两个链接。

## 实现验收标准

- 任意 `.mdx` 内容可以在正文中使用 `GithubRepoCard`，并在对应位置渲染。
- 旧文章不会因为 `github` frontmatter 缺失或 GitHub API 失败而构建失败。
- 文章详情页不再根据 `github` 字段自动追加卡片。
- 构建脚本能发现显式组件中的仓库并刷新或复用缓存。
- 卡片有清晰的 GitHub 标识、项目名称、描述、统计信息和外链入口。
- 浅色、深色、移动端和键盘 focus 状态可用。
- `curl_cffi` 文章遵循本框架，并通过 lint、typecheck、测试和 production build。
- 文章初稿经过 `human-writing` 审查后才标记为公开内容。
